새로 꽂은 Wi-Fi 7 어댑터가 리눅스에서 쓸 만한지 확인하고 iperf3로 속도나
한번 재보자는 것이 시작이었다. 어댑터는 5분 만에 붙었고, 그다음부터 하루가
갔다. 결론부터 쓰면 어댑터 잘못은 하나도 없었다. 문제는 그 위에 얹힌
것들이었다.

중간에 내가 내린 틀린 결론들은 지우지 않고 그대로 뒀다. 소거법으로 파고들
때 어디서 미끄러지기 쉬운지가 오히려 그 부분에 남아 있어서다.

측정 대상은 MT7927(Filogic 380)이고, 호스트는 Ubuntu 26.04에 커널
7.0.0-31-generic, 상대는 OpenWrt AP의 3링크 MLD(2.4G ch6 20MHz / 5G ch100
160MHz / 6G ch37 320MHz)다.

## 6GHz가 안 보이면 규제 도메인부터 본다

`lspci`에 잡히고 `mt7925e`가 붙었고 인터페이스도 올라왔다. 그런데 스캔에
6GHz가 하나도 없었다.

```
$ iw reg get
global
country 00: DFS-UNSET

$ iw phy phy0 info | grep 6135
    * 6135.0 MHz [37] (disabled)
```

규제 도메인이 world(00)면 6GHz는 통째로 잠긴다. `iw reg set KR` 한 줄로
채널이 15 dBm으로 살아났고, 그제서야 AP의 6GHz 링크가 스캔에 나타났다.
안테나나 드라이버를 의심하기 전에 볼 곳이 여기다.

그다음은 환경 정리였다. SSH 원격 세션이라 polkit이 NetworkManager 제어를
거부했고, 유선과 무선이 같은 서브넷에 있어서 라우팅이 꼬였다. 측정할 때는
소스 IP만 지정해서는 부족했다. 인터페이스까지 못 박아야 트래픽이 무선을
탄다.

```
$ iperf3 -c 10.1.1.1 -B 192.168.10.212%wlp3s0 -t 5
...
wlp3s0 TX 증가: 489 MB   enp1s0 TX 증가: 0 MB
```

바이트 카운터로 확인하는 이 과정을 건너뛰면 유선 속도를 무선 속도라고
믿게 된다. `-B <ip>`만 주면 소스 주소는 바뀌어도 라우팅은 여전히 유선을
고른다.

## 첫 숫자가 낮았던 건 드라이버가 인박스가 아니어서였다

첫 측정은 업링크 497, 다운링크 705 Mbps였다. PHY 협상은 2882 Mbps였으니
효율이 20% 남짓이다. AP에서 서버까지 유선은 2.36 Gbps로 뚫려 있었으므로
병목은 무선 쪽이 맞았다. TCP 멀티스트림, 파워세이브, 신호 세기, 호스트
CPU를 차례로 소거했다. 4스트림이 단일 스트림보다 빠르지 않았고(488 대
497), 평균 -37 dBm에 `tx failed 0`, 재전송률 2.1%였다. 혼잡제어나 윈도우
문제였다면 멀티스트림에서 올라갔어야 한다.

그러다 `modinfo`를 보고 멈칫했다.

```
$ modinfo mt7925e | head -2
filename: /lib/modules/7.0.0-31-generic/updates/dkms/mt7925e.ko.zst

$ dkms status
mediatek-mt7927/2.11, 7.0.0-31-generic: installed
```

인박스 드라이버가 아니라 벤더 DKMS 패키지였다. 그것도 2026-04-15자
v2.11이고, 당시 최신은 v2.14였다. 2.14로 올리자 업링크가 705 Mbps로
올라갔다. 바뀐 것은 송신 출력 보고 버그였는데, 2.11에서는 `txpower`가
15.00 dBm으로 굳어 있다가 2.14에서 규제 한도인 23 dBm으로 올라왔다.
규제 도메인을 KR에서 TW로 바꿔 한도를 8 dB 올렸을 때 업링크가 꿈쩍도 하지
않았던 이유가 이것으로 설명된다. 한도만 올라갔고 실제 출력은 따라가지
않고 있었다.

다운링크는 세션 내내 637~1190 Mbps로 흔들렸다. 신호가 같은데 수신 MCS만
8에서 5까지 오르내렸으니 간섭 변동으로 보는 게 맞다. 유의미하게 올라간
것은 업링크뿐이다.

## 조건은 다 맞는데 협상만 160MHz

여기서부터 오래 걸렸다. 확인할 수 있는 것은 다 확인했고, 전부 320MHz를
가리켰다.

| 조건 | 실측 |
| --- | --- |
| AP 운용 폭 | 320 MHz, center 6105 (설정값이 아니라 실제 chandef) |
| AP EHT Operation | Channel Width: 320 MHz |
| AP EHT Capabilities | 320MHz in 6GHz Supported |
| 규제 규칙 (TW) | 5945-6425 @320 MHz |
| 어댑터 능력 | 320MHz in 6GHz Supported, MCS Map BW=320 |
| **협상 결과** | **160 MHz** |

커널은 이런 메시지를 남겼다.

```
wlp3s0: regulatory prevented using AP config, downgraded
```

나는 이걸 근거로 규제 문제라고 결론 내렸다. 틀렸다. 나중에 소스를 보니
이 메시지는 이렇게 나온다.

```c
if (chanreq->oper.width != ap_chandef->width || ap_mode != conn->mode)
        link_id_info(sdata, link_id,
                     "regulatory prevented using AP config, downgraded\n");
```

최종 폭이 AP와 다르기만 하면 원인과 무관하게 찍힌다. 메시지가
"regulatory"라고 적혀 있다고 규제가 범인인 것은 아니다. 커널 메시지도
결국 누군가 손으로 쓴 문자열이다.

## 도구가 보여주지 않는 것

채널에 `no 320MHz` 같은 제한이 걸렸는지 보려고 `iw phy info`를 뒤졌다.
아무것도 없었다. 그래서 규제를 배제했다. 이것도 틀렸다.

나중에 확인해 보니 `iw`는 애초에 그 플래그를 출력할 줄 모른다. 채널
플래그로 문자열을 갖고 있는 건 `no IR` 하나뿐이다. 그래서 nl80211을 직접
파싱하는 도구를 만들어 다시 봤는데 결과가 같았다. 그런데 이번에는 이유가
달랐다. 커널이 이 플래그를 nl80211로 내보내지 않기 때문이었다.

```
5955 MHz 원시 속성:
  FREQ, MAX_TX_POWER, NO_HT40_MINUS, INDOOR_ONLY, OFFSET
  (NO_320MHZ 없음)

같은 시각 커널 내부 chan->flags:
  0x80220 = NO_320MHZ | INDOOR_ONLY | NO_HT40_MINUS
```

사용자 공간에서는 안 보이고 커널 안에서는 켜져 있었다. "도구로 봤더니
없더라"는 근거가 되지 못한다. 그 도구가 그것을 볼 수 있는지를 먼저 확인해야
한다. 나는 같은 함정에 두 번 빠졌다. 한 번은 `iw`로, 한 번은 직접 만든
도구로.

## 커널 안으로

사용자 공간에서 볼 수 없으면 안에서 봐야 한다. 먼저 ftrace로 mac80211이
무엇을 판단했는지 잡았다.

```
drv_add_chanctx: ap(6135MHz, width:13, center 6105)      <- AP는 320MHz로 정확히 파싱
                 chandef(6135MHz, width:5, center 6185)  <- 실제 사용은 160MHz
```

width 13이 `NL80211_CHAN_WIDTH_320`, 5가 160MHz다. 파싱은 정확했고 그
뒤에서 깎였다는 뜻이다. 다음은 kprobe로 판정 함수의 반환값을 봤다.

```
cfg80211_chandef_valid (320MHz)   ret=1   유효
cfg80211_chandef_usable(320MHz)   ret=0   거부
```

여기서 한 번 막혔다. `_cfg80211_chandef_usable()`의 320MHz 분기에서 실패할
수 있는 조건은 몇 개 안 되는데, 내가 실측한 값들은 전부 통과 조건을
만족했다. 관측과 소스가 어긋난 것이다.

그래서 모듈을 디스어셈블해 함수 안 분기마다 주소를 따고 거기에 kprobe를
걸었다.

```
br320 -> bandok -> bittest -> found -> retfalse

서브채널 루프:
  freq=5955000  flags=0x80220  prohib=0x80041  -> pass 없음
  교집합 0x80000 = IEEE80211_CHAN_NO_320MHZ (BIT 19)
```

320MHz 블록의 첫 서브채널인 5955 MHz에서 걸린다. cfg80211이 320MHz를
검사할 때 `NO_320MHZ`를 금지 마스크에 넣는데 채널이 그 비트를 갖고 있으니
즉시 `return false`다. 그러면 mac80211이 한 단계 낮춰 160MHz로 연결하고
아까 그 오해를 부르는 문구를 찍는다.

범인은 찾았다. 6GHz 채널마다 `NO_320MHZ`가 켜져 있었다. 그런데 규제
규칙에도, 드라이버 채널 테이블에도 그걸 설정하는 코드가 없었다.

## 범인은 펌웨어의 CLC였다

남은 경로는 하나였다. mt7925 계열 드라이버에는 CLC(Country Location
Control)라는 기능이 있다. 펌웨어가 담고 있는 국가·지역별 제한 테이블을
드라이버가 읽어 채널 플래그에 덮어쓰는 것이다. 모듈 파라미터로 끌 수 있다.

소스만 보면 CLC 코드는 `NO_EHT`(BIT 20)와 `DISABLED`(BIT 0)만 설정하는
것처럼 보인다. 비트가 안 맞으니 아닐 거라고 생각했다. 세 번째 오판이었다.
실제로는 `NO_320MHZ`(BIT 19)까지 걸린다.

```
$ modprobe mt7925_common disable_clc=1

channel 37 (6135 MHz), width: 320 MHz, center1: 6105 MHz
rx bitrate: 3459.3 MBit/s 320MHz EHT-MCS 8 EHT-NSS 2
```

한 줄로 열렸다. 규제 도메인도 AP 설정도 그대로다.

| 측정 | 160MHz | 320MHz |
| --- | --- | --- |
| TCP 업링크 | 705 Mbps | 1080 Mbps |
| TCP 업링크 4스트림 | 488 Mbps | 1690 Mbps |
| TCP 다운링크 | 637 Mbps | 1380 Mbps |
| UDP 다운링크 손실 | 21% | 0.06% |

손실률 변화가 특히 눈에 띈다. 대역폭이 모자라 밀어내지 못하던 상황이었던
셈이다.

여기에는 분명히 적어둘 것이 있다. `disable_clc=1`은 규제 준수 장치를 끄는
것이다. 실험실 검증 목적에 한정해야 하고, 실제 운용 환경이라면 해당 지역이
6GHz 320MHz를 허용하는지 별도로 확인해야 한다. 위의 320MHz 수치는 전부
이 조건에서 얻은 값이다.

## MLO도 뿌리가 같았다

AP는 3링크 MLD를 정상 운용하는데 STA는 6GHz 하나만 붙었다. 드라이버가
동시 링크 수를 1로 선언하는 자리를 찾아 고쳐 봤지만 아무 변화가 없었다.
그래서 그 위의 게이트를 kprobe로 읽었다.

```
chip_cap = 0x0000000000000000
set bits: (없음)
```

`chip_cap`은 펌웨어가 보내는 `MT_NIC_CAP_CHIP_CAP` TLV에서 채워진다.
MT7927에서는 이게 비어서 온다. 그 결과 능력 게이트가 전부 닫힌다.

| 비트 | 능력 | 영향 |
| --- | --- | --- |
| BIT(4) | 11D_EN | 규제 처리가 `regulatory_hint()` 대신 CLC 경로로 |
| BIT(8) | MLO_EN | `WIPHY_FLAG_SUPPORTS_MLO`가 설정되지 않음 |
| BIT(9) | MLO_EML_EN | EML 비활성 |

내가 고쳤던 동시 링크 수 한 줄은 이 게이트 아래에 있어서 실행조차 되지
않는 죽은 코드였다. 고쳐도 아무 일이 없었던 게 당연하다.

게이트를 강제로 열자 3링크가 전부 붙었다. 링크마다 별도 로컬 주소가
부여됐고 AP 쪽 debugfs에서도 링크 세 개가 확인됐다.

```
wlp3s0: [link 0] local 36:2e:4a:82:fb:df <- AP 06:0c:43:26:60:10  (2.4GHz)
wlp3s0: [link 1] local e6:e0:10:0c:19:3a <- AP 42:0c:43:26:60:10  (5GHz)
wlp3s0: [link 2] local 6a:e0:6c:f5:9a:4a <- AP 00:0c:43:26:60:10  (6GHz, assoc)
```

다만 데이터패스가 불안정했다. 업링크는 1330 Mbps로 올랐는데 다운링크가
1380에서 371 Mbps로 무너졌고 재전송이 718건까지 뛰었다. MT6639는 RF1을
5GHz와 6GHz가 공유하는 구조라, 두 링크를 함께 물리면 수신 경로가 엉키는
것으로 보인다. 업스트림이 MLO 재도입 조건으로 꼽은 나머지 수정들이 빠진
상태와 정확히 맞아떨어진다. 능력 비트만 열어서 될 일은 아니었다는 뜻이다.

## 배운 것

어댑터는 문제가 없었다. MT7927 하드웨어는 320MHz도 MLO도 능력을 갖고
있고, 커널과 드라이버에도 관련 코드가 다 있다.

막고 있던 것은 펌웨어의 보고였다. 320MHz는 CLC가 채널마다 `NO_320MHZ`를
새겨서 막혔고, MLO는 `chip_cap`이 0으로 들어와 능력 게이트가 닫혀서 막혔다.
둘 다 펌웨어 레벨이고 뿌리가 같다.

그리고 그 사실은 사용자 공간에서 보이지 않았다. `iw`로도, 직접 만든
nl80211 도구로도 보이지 않는 플래그였다. ftrace와 kprobe로 커널 안을
들여다보기 전까지는 "AP도 규제도 어댑터도 다 맞는데 왜 안 되지"라는
상태에 계속 머물러 있었다.

틀렸던 것들을 모아 보면 이렇다.

| 판단 | 실제 |
| --- | --- |
| 드라이버가 320MHz를 미구현 | 구현돼 있었고 이 결정에 관여조차 안 함 |
| 규제 도메인 문제 | 메시지 문구에 속았음. 규제 규칙은 결백 |
| 채널에 제한 플래그 없음 | 도구가 그 플래그를 못 볼 뿐이었음 |
| CLC는 비트가 안 맞으니 아닐 것 | CLC가 범인이었음 |
| AP의 FD 고갈로 서비스 다운 | 내가 만진 라우팅이 원인이었음 |

다섯 중 넷은 "확인했다고 믿었지만 확인이 아니었던" 경우다. 소거법은 각
후보를 실제로 관측할 수 있을 때만 성립하는데, 관측 수단이 그 후보를 볼 수
없다는 사실 자체를 나는 마지막에야 알았다. 다음번에는 도구를 믿기 전에
도구가 무엇을 출력할 수 있는지부터 확인할 생각이다.

재현에 쓴 명령은 이게 전부다.

```sh
# 6GHz 열기
sudo iw reg set TW

# 320MHz 열기 (실험실 한정)
sudo modprobe mt7925_common disable_clc=1

# 무선 강제 측정
iperf3 -c <server> -B <wifi-ip>%wlp3s0 -t 10 -P 4

# 커널 안 보기
echo 'p:usa cfg80211_chandef_usable width=+8($arg2):u32 prohib=$arg3:x32' \
  > /sys/kernel/tracing/kprobe_events
```

측정 환경은 MT7927(Filogic 380), Ubuntu 26.04 커널 7.0.0-31-generic,
mediatek-mt7927 DKMS 2.14-6, OpenWrt AP 커널 6.18의 3링크 MLO다. 모든
수치는 10초 실행 기준 단회 측정이고, 다운링크는 세션 중 간섭에 따라
637~1390 Mbps로 흔들렸다.
