8MB 플래시, 64MB RAM의 MT7628(MIPS 24Kc) 기반 상용 라우터를 OpenWrt 24.10으로 만들고 있다.
이 제품의 웹 UI는 오랫동안 LuCI 위에 있었는데, 페이지를 하나 옮길 때마다 눈에 띄게 버벅였다.
이번에 LuCI를 이미지에서 완전히 걷어내고, 브라우저 런타임을 직접 만든 것(`ls-webui`)으로
교체했다. 서버 쪽에는 CGI도, 디스패처도, 템플릿도 없다. uhttpd가 정적 파일을 서빙하고
`/ubus`로 JSON-RPC를 중계하는 것이 전부다.

결과부터 말하면 로그인 화면은 459ms에서 48ms로, 페이지 이동 고정비용은 368ms에서
6ms(이후 캐시 0)로 줄었고, **기존 뷰 57개는 한 줄도 고치지 않았다.**

이 글은 그 과정에서 무엇을 계측했고, 왜 이 구조를 골랐고, 어디에 함정이 있었는지의 기록이다.

## 1. 범인을 계측으로 잡다

"LuCI가 느리다"는 말은 흔하지만, 정확히 무엇이 느린지는 재보기 전까지 몰랐다.
실기에서 TLS 핸드셰이크(128ms)를 차감한 순수 서버 시간을 재봤다:

| 요청 | 서버 시간 |
|---|---|
| 정적 파일 | ~2–10 ms |
| `/ubus` JSON-RPC | ~5 ms |
| `/cgi-bin/luci/` | **430 ms (warm) / 3,400 ms (cold)** |

uhttpd 자체는 죄가 없다. 정적 파일도 빠르고, uhttpd에 내장된 `/ubus` 중계도 빠르다.
느린 것은 오직 LuCI 디스패처 경로다. 디스패처는 매 페이지 이동마다 fork되어
`menu.d/*.json`과 `acl.d/*.json`을 전부 다시 파싱한 뒤에야 첫 바이트를 낸다.
MIPS 580MHz 싱글코어에서 이 비용이 요청마다 반복된다.

그렇다면 결론은 자명하다. **fork를 없애면 된다.** LuCI를 최적화하는 게 아니라,
fork되는 경로 자체를 제거하는 것.

> 계측 자체에도 함정이 하나 있었다. curl의 `--next`는 이 조합(uhttpd + TLS)에서
> 연결을 재사용하지 않는다. 매번 `num_connects=1`이라 핸드셰이크 125ms가 모든
> 측정을 삼킨다. Python `http.client`로 연결을 직접 유지해야 서버 시간이 보였다.

## 2. 구조: 서버에서 코드를 없앤다

```
브라우저 ──HTTPS──► uhttpd (fork 없음)
                     ├── /                → index.html (정적 셸)
                     ├── /ls-static/*     → 런타임 JS·CSS·menu.json·i18n (정적)
                     ├── /ubus            → in-process JSON-RPC ─► rpcd ─► uci/file/session/…
                     └── /cgi-bin/cgi-*   → cgi-io 전용 (펌웨어 업로드·백업 다운로드)
```

핵심 관찰은 이것이다: LuCI의 최신 뷰들은 이미 클라이언트 사이드 렌더링이다.
브라우저에서 JS가 돌고, 데이터는 ubus로 가져온다. 서버의 LuCI가 실제로 하던 일은
메뉴 트리 조립, ACL 검사, 최초 HTML 셸 생성 정도인데, 전부 미리 계산해 두거나
클라이언트로 옮길 수 있는 일이다.

- HTML 셸은 정적 파일 하나로 박아둔다
- 메뉴 트리는 부팅 시 한 번 `menu.d/*.json`을 병합해 `/www/ls-static/menu.json`으로
  구워둔다 (오버레이 마모를 피하려고 내용이 바뀔 때만 기록)
- ACL/세션은 원래부터 rpcd와 uhttpd의 몫이었다. uhttpd의 `/ubus` 중계가
  세션 토큰으로 권한을 검사한다. LuCI가 없어도 이 층은 그대로 남는다
- i18n은 `.po`를 `.lmo`로(디스패처가 mmap) 바꾸는 대신 `.po`를 JSON으로 변환해
  브라우저가 언어당 1파일을 fetch한다

유일하게 CGI로 남긴 것은 `cgi-io`다. 펌웨어 이미지 업로드와 백업 다운로드는
JSON+base64로 `/ubus`에 태울 수 없는 덩치라서, 파일 전송 전용 CGI 둘만 남겼다.

## 3. 뷰 57개를 한 줄도 안 고치는 호환층

이 전환이 현실적이었던 이유는 하나다. 뷰들이 실제로 쓰는 LuCI 클라이언트 API를
전수 조사해 보니 **43개 심볼**이 전부였다 (`form.*`, `ui.*`, `uci.*`, `rpc.*`,
`fs.*`, `L.*`). 설치 경로와 이 43개 심볼의 시그니처를 유지하는 런타임을 새로 쓰면,
기존 뷰 57개와 테마가 무수정으로 동작한다.

125KB짜리 `network.js` 같은 무거운 모듈도 필요 없었다. 뷰들이 부르는 `network.*`는
알고 보니 ubus 객체명이지 클라이언트 모듈이 아니었다.

덤으로 얻은 것도 있다. 같은 동기 블록에서 나간 ubus 호출들을 마이크로태스크에서
모아 HTTP 1회로 배칭하게 했더니, 상태 페이지의 6개 호출이 왕복 1회(개별 280ms,
배치 72ms)로 줄었다. 디스패처 시절에는 구조적으로 불가능했던 최적화다.

## 4. 세션: 쿠키가 없으면 CSRF도 없다

세션 처리는 오히려 단순해졌다. 쿠키를 쓰지 않는다. 세션 id는 JSON-RPC 페이로드
안에 들어 있고 uhttpd가 그것으로 인증한다. 요청에 주변(ambient) 자격증명이 붙지
않으므로 CSRF라는 문제 자체가 성립하지 않는다.

대신 실사용에서 "로그인이 자꾸 풀린다"는 증상을 쫓다가 두 가지 원인을 찾았다:

1. 갱신 주체 부재. rpcd는 세션을 사용할 때마다 TTL을 리셋해 주는데, 페이지를
   열어둔 채 놔두면 아무도 세션을 건드리지 않아 1시간 뒤 편집 도중 튕긴다.
   그래서 세션 수명의 1/3마다 keepalive(`session.get`)를 보내게 했다.
2. `-32002`를 만료로 오해. uhttpd는 "세션 만료"와 "이 호출에 권한 없음"을
   똑같이 `-32002 Access denied`로 답한다. ACL에 빠진 호출 하나가 섞인 페이지를
   열면, 멀쩡한 세션을 클라이언트가 스스로 끊어버렸다. 그래서 이제 `-32002`는
   세션 생존 확인(probe)만 트리거하고, 그 결과로만 로그아웃한다.

## 5. 지뢰밭: LuCI를 빼면 조용히 사라지는 것들

이 전환의 진짜 비용은 코드 작성이 아니라, LuCI가 암묵적으로 제공하던 것들을
찾아내는 일이었다. 전부 "에러 없이 조용히" 사라진다는 공통점이 있다.

- `luci`라는 ubus 객체는 `rpcd-mod-luci`가 아니라 luci-base 소속이다.
  이름만 보면 당연히 전자 같지만 아니다. luci-base를 빼는 순간 `setPassword`
  (비밀번호 변경 페이지!), `getConntrackList`, `getTimezones`, `getInitList`,
  `setInitAction`, `setLocaltime` 6개가 사라진다. 이 6개만 ucode rpcd 플러그인으로
  다시 구현했다.
- 스위치 페이지의 백엔드도 같은 뿌리. `getSwconfigFeatures`/`getSwconfigPortState`가
  luci-base 것이라 함께 사라져, swconfig 스위치의 하드웨어 상태를 읽을 방법이
  없어졌다. rpcd 스크립트로 ubus `switch` 객체를 신설했다.
- rpcd의 `uci.commit`은 `config` 인자가 필수다 (없으면 status 2로 실패).
  LuCI 런타임이 알아서 해주던 부분이라 몰랐고, 그 결과 한동안 **모든 페이지의
  Save & Apply가 아무것도 커밋하지 않고 있었다.** `uci.changes`로 변경된 config
  목록을 받아 하나씩 커밋해야 한다. `revert`도 마찬가지.
- `file.stat`은 `read`가 아니라 `list` 권한을 요구한다. luci-base의 ACL이
  `"/": ["list"]`를 슬쩍 넣어주고 있었다. 빼먹으면 파일 존재 확인이 전부 죽는다.
- `L.env.cgi_base` 같은 환경값을 디스패처가 주입하고 있었다. 빈 문자열이 되면서
  펌웨어 업로드·백업 다운로드·복원이 전부 404였다 — cgi-io를 남겨둔 바로 그 세 기능이.

## 6. "렌더링된다 ≠ 동작한다"

가장 비싼 교훈. 뷰 57개가 전부 렌더링되는 것을 확인하고 끝난 줄 알았는데,
실기 전수 검증에서 저장·적용·업로드 경로의 버그가 10건 나왔다. 위의 uci.commit 건,
cgi_base 건이 대표적이다. 화면은 완벽한데 Save & Apply가 no-op이었다.

렌더링 스윕은 데이터 읽기 경로만 검증한다. 쓰기 경로(save/apply/rollback),
파일 전송, 그리고 "적용 후 연결이 끊기는" 롤백 시나리오는 전부 별개 경로라
실기에서 직접 태워봐야 했다. 특히 주소를 바꾸는 적용은 롤백 확인(confirm)이
구조적으로 불가능하다. confirm은 기존 주소의 세션으로 가는데, 새 주소에는
그 세션이 없다. 이건 미리 감지해서 사용자에게 무보호 적용을 제안하는 것으로 풀었다.

## 7. 결과

같은 하드웨어 2대로 A/B 측정 (TLS 핸드셰이크 제외, 연결 재사용):

| | LuCI | ls-webui |
|---|---|---|
| 로그인 화면 | 459 ms | **48 ms** |
| 페이지 이동 고정비용 | 368 ms **매번** | **6 ms**, 이후 캐시 0 |
| 상태 데이터 6콜 | — | 배치 72 ms (개별 280 ms) |
| 첫 진입 전송량 | 313 KB | 267 KB |
| 동시 요청 52건 | ucode fork 3개 + 대기 | **fork 0** |
| /www 크기 | 1,229 KB | 778 KB |
| 이미지 크기 | — | 압축 기준 **−315 KB** |

8MB 플래시에서 315KB는 체감되는 숫자다. 정지 상태 RAM은 굳이 주장하지 않는다.
측정 조건이 달라 비교가 불분명했고, 이 구조의 이득은 "요청당 fork가 없다"이지
상주 메모리가 아니다.

## 8. 언제 이 방법이 맞나

이 접근이 성립한 전제를 분명히 해두는 게 공정할 것 같다:

- 뷰가 이미 클라이언트 사이드 렌더링이었다. 구식 서버 템플릿 뷰가 많았다면
  호환층으로 될 일이 아니다.
- 필요한 서버 기능이 전부 rpcd/ubus에 이미 있었다. 없던 것(스위치 상태 등)은
  rpcd 스크립트 플러그인으로 채웠는데, 이건 LuCI가 있어도 어차피 해야 하는 일이다.
- UI를 우리가 통제한다. 제품 이미지라 뷰 목록이 닫혀 있다. 임의의
  luci-app-*를 설치할 수 있어야 하는 범용 배포판이라면 얘기가 다르다.

반대로, 저사양 SoC에서 자체 UI를 가진 OpenWrt 제품을 만들고 있다면, 디스패처
fork 비용은 하드웨어를 바꾸지 않고 없앨 수 있는 가장 큰 성능 예산이었다.
그리고 그 작업의 대부분은 코드 작성이 아니라, LuCI가 조용히 해주던 일들의
목록을 만드는 것이었다.
